# The corpus

This directory is the body of what runs established about this engine, the
apparatus that produces it, and what those runs left behind. The specs are
`docs/spec/ktema-corpus-0.1.md` and `docs/spec/ktema-evidence-0.1.md`; the plan and
its state are `master.md`. Where this file and a spec disagree, the spec wins.

The corpus is an observer. It records what a run left behind and takes no part in
the run: nothing here measures, and nothing here is linked into what is measured.
An observation is a record, so it carries a revision and an instant, and two
observations of one subject are comparable rather than contradictory.

## What this directory holds

| Part | Holds | Removal test |
|---|---|---|
| `vol` | records in key order, one JSON file each, and nothing else | every file is a record whose key is its path |
| `out` | what a run produced: takes and reports | losing it costs the footage, not the evidence |
| `assembly/` | the corpus's own code: it loads what each stack left and assembles records from it | removing it stops the volume being written |
| `export/` | the rows a page reads, derived from `vol` | regenerated by `assembly/export.sh`; tracked so a copy elsewhere can be compared |
| `docs/` | the statements the center makes, one markdown document each | a document is a fact in the form a person reads, so it is content and not a record |

There is no producer in this directory. `demo/`, `bench/`, and `trial/` at the root
write into `out`; `crates/` and `verify/` are the subject. That is what lets this
directory move to a repository of its own without taking the engine or a recorder
with it.

The test for `assembly/` is that it assembles and never measures. Anything that
measures belongs with the stack it measures. `assembly` rather than `engine`
because `engine` names the subject in every other sentence.

`out` is not tracked. `vol` is.

`vol` is a ktema volume, written by the engine and read by it:

```text
format                          the volume's version
facts/f_<coordinate>.fact       a record, and the coordinate is computed from what it holds
blob/<sha256>.bin  .bin.meta    the payload, and its media type
```

A record is deposited by name, which is its key, and the engine answers that name with the coordinate. The address is
60 base-36 digits, three to an axis. Nothing here writes a file: `assembly/land.sh` asks the daemon for
`write_fact_named` and `assembly/export.sh` asks it for `list` and `read_payload`, so the record layer and its
storage are the same implementation.

`corpus/assembly/migrate.sh` is the one-time move that turned the earlier directory of JSON files into this volume.

## The rule

A record is written by a run, never authored by hand. If you are typing a number
into a page or into `vol`, the flow has been broken somewhere earlier.

A landed record is immutable. Its key ends in the instant it happened, so a second
run on one revision is a second file and the first stays. Editing a landed record
is not a correction, it is a lost history.

A page holds no number of its own. It cites the key of the record it draws, and a
page that cites none is a selection of intents.

## The record

| Field | Meaning |
|---|---|
| `activity` | `bench`, `demo`, `trial`, or `verify` |
| `subject` | the stable name the producer already uses |
| `platform` | `bare-metal`, `fpga`, `host`, `browser`, `rtos`, or `microkernel` |
| `target` | the triple the run compiled for, where it compiled |
| `revision` | the commit, with `+` when the tree was dirty |
| `created` | ISO 8601 in UTC |
| `class` | `exhaustive` when the run covers its declared space, `partial` otherwise |
| `claim` | one sentence, built from the payload where the payload has the numbers |
| `payload` | the run's output, as one string, so the digest is over the bytes written |
| `content_hash` | `sha256` over the payload exactly as written |
| `parameters` | the run's knobs: sizes, seeds, cut lengths |
| `object` | a produced file's path and digest, for a payload that is a file |
| `parent` | the key this record refines. Singular in 0.1, so a node with two sources waits on 0.2 |

The key is its path under `vol`:

```text
<activity>/<revision>/<platform>/<subject>/<created>
```

Every segment is a prefix, so one listing answers a subject's history, a
platform's runs, or every run at a revision. A benchmark is `partial` by
construction; a record that called one exhaustive would have moved a sample into
an oracle, which the evidence spec forbids.

## The flow

```text
a run  →  vol  →  export  →  a page
```

| Step | Command | Writes |
|---|---|---|
| measure | manual: `./run.sh --bench [records...]` | `out/bench/volume-sweep/<created>/` with a manifest and a payload, then lands and exports |
| land | `corpus/assembly/land.sh` | `vol/<activity>/<revision>/<platform>/<subject>/<created>.json` |
| declare | `corpus/depends.json` | which subject each claim rests on; carried into the export |
| export | `corpus/assembly/export.sh` | `export/bench.json`, one entry per subject, the latest by `created`; `export/corpus.json`, every record and the declaration |
| check | `corpus/assembly/land.sh --check`, `corpus/assembly/export.sh --check` | nothing, exits non-zero |

The export is what a page reads. A site keeps a copy because the trees are
separate, and the copy carries the key so the page can cite it.

A measurement is triggered by a person and by nothing else. Everything after it
reads the volume, so a publish or a page rebuild never needs a run, and the flow
exercises itself against what is already accumulated.

A claim rests on subjects, and `depends.json` states which. A subject with no
current record leaves the claim unbacked; a claim absent from the file is
undeclared, and its state is `unknown` rather than guessed. The export carries the
declaration, so a reader can tell a claim that has nothing behind it from one whose
evidence is older.

## The inbox

A producer states what its run was; the assembler places it. That is the whole
contract, and it is why an adapter that talks to a board lives with the stack and
not here.

```text
out/<activity>/<subject>/<created>/
  manifest.json    activity, subject, platform, revision, created, class, claim, parameters
  payload          the run's output, with no trailing newline
```

The manifest carries what only the producer knows: the revision it ran at, whether
the tree was dirty, the sentence the run establishes, and the knobs it used. A
manifest that does not state `activity`, `subject`, `revision`, `platform`,
`created`, `class`, or `claim` is refused instead of guessed at.

The payload has no trailing newline so that the digest of the file is the digest of
the bytes the record carries. A producer that writes a JSON report normalises it
with `jq -cS . report | tr -d '\n'`.

A run that borrowed a number from another check states where it came from, in
`parameters`. A number with no owner is one nobody can trace.

## Adding an activity

A new activity is a producer outside this directory, such as `demo/`, that writes
bundles into `out/<activity>/<subject>/<created>/`. `land.sh` needs no change for it:
the bundle says what it is. The page reads the export, which is built from `vol`.

## Who does what

| Actor | Does | Never does |
|---|---|---|
| ktema | writes a record when a run happens | reads |
| kletos | aggregates records and answers over a volume | invents a number |
| an analyst, a model or a person | reads records and writes a derived record | stays in the read path |
| Delta | reads a volume and draws it | calls a model |

A model writes at ingestion. What it concludes becomes a record with its own key
and the keys it derived from, so the conclusion is readable afterwards without
the model and checkable by a person.

## The states

A record is true of the revision it names. Whether it is still true has four
answers: `current`, `shape-current`, `stale`, `unknown`. These need two things
that do not exist yet, a `depends` line per subject and the shape of each revision
kept as a record, so nothing computes them today.

## What is live

`demo` and `bench` are current. `trial` is built and waiting on a party; its gate
still runs. `verify` is the engine's own gate and lives outside this directory.
